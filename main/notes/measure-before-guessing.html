登入頁「第 2 秒卡一下」：修了七輪都沒好，直到我改成先量再猜

2026-09　・　儀器軟體／效能

  • PyQt
  • 效能剖析
  • GIL
  • 圖片解碼
  • 快取

Claude 協作 / CoDev with Claude

症狀

每次開啟桌面程式，登入頁出現後大約第 2 秒，整個動畫會「重重地卡一下」，然後才順順地跑。這個問題被回報了很久。前面我們已經查了七輪：修掉多餘的語言切換廣播、把頁面建構時的搶先查詢移到顯示之後、量化單幀的繪製成本……每一輪都修對了一件事，但那一下重卡頓一直都在。

這次不猜，直接量

在不開視窗的模式下跑真實的啟動路徑，在主執行緒掛一個 1 ms 的計時器當「停頓偵測器」：它每次觸發時，看距離上一次隔了多久，超過門檻就記一筆。同時把所有可疑事件（重量級的 import、垃圾回收、各個載入回呼、背景繪製……）的時間戳記，全部放到同一條時間軸上。

# 主執行緒掛一個 1ms 計時器，量「兩次觸發之間」實際隔了多久（示意）
last = time.perf_counter()

def tick():
    global last
    now = time.perf_counter()
    if now - last > 0.030:                 # 超過 30ms 視為一次停頓
        stalls.append((now - T0, now - last))
    last = now

timer = QTimer()
timer.setInterval(1)
timer.timeout.connect(tick)
timer.start()

結果非常乾淨：最嚴重的停頓是 268 ms，發生在視窗顯示後 2385 ms，也就是使用者說的「第 2 秒」；而同一個時間點上，主執行緒正在跑一個品牌資料的載入回呼，耗時 255 ms。做 A/B：把 LOGO 的資料抽掉再跑，最嚴重的停頓降到 32 ms。

根因

客戶上傳的自訂 LOGO，尺寸是 3871 × 3853，約 1490 萬像素。PNG 壓縮後只有 179 KB，看起來很小；但解碼後約 59 MB，而且在整個執行期間常駐記憶體，解碼一次約 150 ms。更諷刺的是，全專案只有一個地方用到它：把它畫進側邊欄一個 34 × 34 的徽章。

為什麼前七輪沒抓到

  • 修對了函式，修錯了那一半。多餘的語言廣播和真正重的圖片解碼，在同一個回呼、同一個時間點，但我修的是小的那一半，重的那一半原封不動。
  • 其中一次的實機 log 其實已經拍到這一筆（約 293 ms），當時被歸因到另一個功能，移掉那個功能後沒有改善，就更確定「不是它」，卻沒有回頭問「那它到底是什麼」。
  • 我一度正確地用數據推翻了「背景匯入搶 GIL」的假設，但推翻之後，注意力全轉向結構性的單幀成本，沒有人再問「第 2 秒那一下是什麼」。

一個被實測推翻的第一直覺

我的第一反應是：把解碼丟到背景執行緒就好。實測不行。用「背景執行緒解碼、主執行緒 1 ms 計時器量停頓」直接量：主執行緒照樣被卡 152 ms。原因是 PNG 解碼是 CPU 密集的工作，而這個函式呼叫從頭到尾佔著 GIL，不會週期性釋放，換哪條執行緒跑，主執行緒都一樣被卡。「移到背景執行緒」對這個症狀幾乎沒用。

修法：不要在冷啟動時解碼那張圖

  1. 本機快取（主要修法）：第一次執行時，下載、解碼、縮到 256 px，存成一張小 PNG；之後只要網址沒變，就直接讀那張小圖（實測約 4 ms）。LOGO 被換過才重新處理。
  2. 上傳當下先縮：之後任何一次重新上傳，伺服器上存的原圖都不會超過 512 px，連快取沒命中的那一次，解碼都是便宜的。
  3. 載入回呼裡，主執行緒只剩一次很便宜的格式轉換（約 1 ms）。

結果

情況圖片處理耗時顯示後最嚴重的停頓
修法前在主執行緒約 140～270 ms，發生在約 2.2 秒
第一次（冷快取）約 688 ms，在背景執行緒約 180 ms（一次性）
之後每次（暖快取）約 4～9 ms約 75 ms，全落在開頭 900 ms 內

顯示後第 2 秒那個時間點，已經完全沒有停頓，被回報的那一下重卡頓消失了。

還沒處理的（刻意）

  • 「開頭一兩秒感覺不到 60 fps」是結構性的單幀成本，和這次的一次性重卡頓是兩件事。
  • 使用者按「儲存」時，仍然會在主執行緒上處理一次大圖。那是使用者主動的一次性動作，不是這次要修的症狀，所以範圍上沒有一起動。
  • 我們一直用附帶除錯器的方式執行程式，而除錯器會追蹤每一個 Python callback。用「不附除錯器」的方式跑一次對比，是零成本的自測，但至今沒有做，所以殘餘的掉幀有多少是除錯器造成的，還不知道。

帶走的幾件事

  • 先量，再猜。把停頓和事件放在同一條時間軸上，答案常常自己跳出來。
  • 「這個函式慢」和「這個時間點的整包工作慢」是兩回事。修對一半，症狀不會消失，而且會讓你以為方向錯了。
  • 圖片壓縮後的檔案大小，跟解碼成本毫無關係。使用者上傳的任何圖片，都該在進入系統的那一刻就縮到用得上的大小。
  • 在丟給背景執行緒之前，先確認那個呼叫會不會釋放 GIL。
