偶發的「讀回不一致」：一次傳輸層封包框架的錯位

2026-09　・　儀器軟體／通訊協議

  • TCP
  • socket
  • 封包框架
  • Python
  • 單元測試

Claude 協作 / CoDev with Claude

症狀

PC 端用 TCP 對儀器寫入一長串設定（拆成數百次小封包的往返），寫完會再讀回來比對。結果有時候會跳出「讀回不一致」，重送一次又好了。不是儀器壞掉，也不是資料有問題。

為什麼偏偏是「有時候」

設定的步驟越多，往返次數就越多：這個案例要走數百次往返，每次還睡 20 ms，光睡眠就超過 8 秒；同一段時間裡，背景輪詢執行緒還在搶同一條連線（這台儀器只有單一 socket）。往返次數越多，中間出一次差錯的機率就越高，所以步驟少的設定幾乎不會遇到。

三個會造成錯位的地方

1. 逾時把收到一半的封包丟掉（最嚴重）

舊版的「收滿 N 個 byte」函式用區域變數當緩衝，逾時就直接回傳失敗。已經收到的半包留在 socket 裡沒人管，之後每一次 recv 都從封包中間開始，偏移固定的 byte 數，而且永遠不會自己恢復。修法是把緩衝存到物件上，逾時時不丟，下次呼叫接著收：

def _recv_exact(self, n):
    # 緩衝存在物件上：逾時不丟掉已收到的半包，下次接著收
    while len(self._rxbuf) < n:
        chunk = self._sock.recv(n - len(self._rxbuf))   # 逾時會丟 socket.timeout
        if not chunk:
            raise ConnectionError("closed")
        self._rxbuf += chunk
    data, self._rxbuf = self._rxbuf[:n], self._rxbuf[n:]
    return data

2. 重送前沒有清管線

上一次逾時後才姍姍來遲的回覆，還躺在緩衝區。重送之後它會被當成「這次的 ACK」，而且位址一模一樣，檢查一定通過。修法是每筆交易開頭、每次重送前都先把殘留清掉。所有 I/O 都在同一把鎖裡，所以交易開始時還留著的資料，一定是上一筆遲到的，清掉是安全的。

3. ACK 只比對位址的低 2 個 byte

改成比對完整的 24 位元位址；讀取也開始比對。回的是別筆交易的封包，就丟掉並清管線，而不是把別人的資料當成這一筆的內容回傳。

有一件事我刻意沒做：不比對指令碼。規格沒寫回覆會不會回傳指令碼，沒有實機可以驗證之前不加；猜錯的話，會把正常的回覆全部判成失敗。

順帶修掉兩個讓它更難查的問題

  • log 的 handler 掛錯地方：只掛在某個具名 logger 上，但大部分模組用的是 logging.getLogger(__name__)，它們往 root 傳、root 沒有 handler，所以那些模組的 log 從來沒有進過檔案。對話框叫使用者「去看日誌」，日誌裡卻什麼都沒有。改成 handler 掛在 root。
  • 對話框直接說差在哪：記錄「第幾步不符、第一個差異在第幾個 byte、寫入值與讀回值」，結果視窗直接顯示，不用再叫人翻日誌。

怎麼確認修對了

用假 socket 重現三種情境：半包逾時、遲到的回覆、長串寫入中間有一次沒回，共 21 個測試。對舊版程式碼跑，14 個失敗；修好後全部通過。這一步很重要，它確認測試測的是真的行為，不是同義反覆。

還沒做的，以及誠實的限制

把每個封包塞更多資料、讓往返次數從數百次降到幾十次，是最直接降低出錯機率的辦法，但需要接上真實的板子驗證，所以我沒有動預設值。另外，寫這篇的時候，這次修正尚未經過實機驗證，只通過了假 socket 的測試。

帶走的幾件事

  • 「偶發」的錯誤通常是在說：某個狀態不會自己恢復，而且和次數有關。先問「什麼東西被留下來了」。
  • 驗證「回覆屬於這次請求」不能只靠位址的一小部分；而且發現不對時，要清掉管線，不是繼續往下讀。
  • 先把「看不到 log」這件事修好，後面的偵錯才有依據。
