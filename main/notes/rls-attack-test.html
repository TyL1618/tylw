自己攻擊自己的系統：權限收緊的遷移，反而開了一扇後門

2026-07　・　儀器軟體／資安

  • PostgreSQL
  • RLS
  • Supabase
  • Python
  • 資安測試

AI 協作標示　這個專案是我與 AI 助手（Claude）協作開發的。本文依專案的開發紀錄整理，文字由 AI 協助撰寫，經我審閱後發布。文中不含公司、客戶或機型名稱，程式碼皆為示意。

背景

這個桌面程式有三種角色，原本的權限只在介面上擋：沒有權限的人，按鈕是灰的。我們把它改成資料庫層的列級安全（RLS），讓資料庫自己拒絕不該有的寫入。之後我要求從「內部人員濫用」和「外部入侵」兩個面向各檢查一遍。

這篇記錄的不是理論推測，而是真的執行過攻擊測試、真的打穿的結果。每一項都是先實測成功、修補後再實測失敗。

1. 最嚴重，而且是遷移本身造成的

那次遷移裡，新帳號註冊時會觸發一個函式，替使用者建立資料列。函式直接信任客戶端傳來的使用者中繼資料裡的 role 欄位。結果：任何人，只要拿得到內嵌在安裝檔裡的公開金鑰（不需要任何既有帳號），就能這樣做：

  1. 註冊時帶上 role = system_admin，成功。
  2. 資料庫裡真的多出一筆管理者。
  3. 用它登入，成功寫入受保護的資料表。

也就是說，整套收緊，攻擊者多打一次註冊就完全繞過。這是我們在遷移時引入的設計缺陷，不是既有程式碼的問題。

修法：改成邀請制。role 不再由客戶端決定：

  • 新增邀請表，開啟 RLS 但刻意不建立任何 policy：客戶端連讀都讀不到，只有用 SECURITY DEFINER 定義的函式碰得到。
  • 發邀請的 RPC 在內部檢查呼叫者是不是管理者，這才是真正的防線。
  • 註冊函式只從邀請表拿角色（15 分鐘有效），完全不看客戶端傳的中繼資料；沒有有效邀請就丟例外，整筆交易回滾。
  • 保留一個啟動條件：整張使用者表完全是空的時候，第一位註冊者自動成為管理者，否則新環境會沒人能發邀請，變成死鎖。
  • 附帶好處：不必靠「記得去後台關閉公開註冊」這種容易忘記的手動步驟。

2. 匿名就能讀走機台清單與帳號清單

修補前，只要有那把公開金鑰，匿名就能讀到完整的機台清單（含負責人的真實姓名）和完整的帳號清單（使用者名稱加角色，方便針對性攻擊）。把 SELECT policy 從「任何人」改成「必須已登入」。

有一張設定表我刻意維持公開讀取，不是漏掉：它在使用者登入之前就要被讀取（顯示客製的名稱），收緊會讓登入頁壞掉。這種「刻意的例外」要寫下來，否則下次檢查的人會把它當成漏洞。

3. 檔案儲存匿名可以列出、上傳、刪除

實測：匿名可以列出、上傳、刪除兩個 bucket 裡的檔案，等於能把所有機台照片和公司標誌刪掉，或換成任意內容。奇怪的是，原本的 SQL 裡根本沒建過 DELETE 的 policy，代表手動在後台設定時留下過名稱不明的寬鬆規則。重建後：讀取維持公開（照片靠公開網址下載），新增、更新、刪除收成只有管理者。

踩到的坑：儲存區 policy 裡呼叫的函式，一定要加 public. 的 schema 前綴。儲存的請求不走 PostgREST，search_path 和一般資料表的 policy 不一樣，不加前綴會找不到函式。

4. 停用帳號的三道防護

原本的停用函式只檢查「呼叫者的角色」，完全不檢查對象是誰。所以可以停用自己（把自己鎖在門外）、低權限的管理者可以停用高權限的管理者。補上三道防護，並新增重新啟用。我也誠實記錄了一個發現：「不能停用最後一個管理者」這道防護實際上不可能被觸發，因為要走到那裡，呼叫者本身就必須是管理者，而前面的檢查已經擋掉了其他情況。

5. 同一類問題的第三次：介面與資料庫不一致

資料池的「新增數據」，任何角色都能按，但資料表在遷移後已收緊成只有管理者可寫。一般使用者按下去，只會拿到一個看不懂的資料庫錯誤。這已經是同一類問題的第三次。教訓：每次收緊一張表的 RLS，就要把 App 裡所有會寫這張表的入口一併清點，介面上要同步擋。

修補前後

測試修補前修補後
匿名註冊成管理者成功被擋下並回滾
匿名讀機台資料（含姓名）讀到0 筆
匿名讀帳號清單全部列舉0 筆
匿名上傳或刪除檔案成功被拒絕
公開網址下載照片可可（沒有被收緊弄壞）
管理者用邀請制建帳號—成功
進階管理者停用系統管理者成功被擋下

檢查過、沒有問題的

  • SQL injection：動態拼接的 SQL 只用在資料表名稱，而表名全部來自寫死的字典，不是使用者輸入；所有「值」都用參數化。
  • log 檔：沒有密碼或金鑰。

帶走的幾件事

  • 資安修補本身，是最容易引入新漏洞的地方。修完一定要用「攻擊者」的角度再測一次，不是只測「正常使用者還能不能用」。
  • 實測攻擊勝過推論。「理論上擋得住」和「我試過了、被擋下」是兩種不同強度的結論。
  • 永遠不要信任客戶端傳來、而且攻擊者可以任意填寫的欄位（例如使用者中繼資料）。
  • 內嵌在安裝檔裡的金鑰，一律當作公開的。真正的防線在資料庫那一側。
  • 刻意的例外要記錄成「刻意」，不然就會被當成漏洞，或被別人「順手修掉」而弄壞功能。
