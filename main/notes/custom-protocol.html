看起來像 Modbus，其實不是：接手新機台前先做的五件事

2026-09　・　儀器軟體／通訊協議

  • 通訊協議
  • TCP
  • 封包分析
  • Python

我是軟體背景，現在負責儀器端的整套軟體。第一次接手新機台，PC 端的操作模式是「用 TCP 連線，然後讀寫暫存器」，這跟 Modbus TCP 長得一模一樣，所以我很自然地拿 pymodbus 這類標準函式庫去連，結果連不上。

後來才搞清楚，那台機器用的是自訂封包格式，只是外觀像 Modbus。更糟的是，幾個月後換了另一個專案，我又犯了一次同樣的錯。這篇是我事後整理出來的檢查清單，目的是讓第三次不會發生。

AI 協作標示　這個專案是我與 AI 助手（Claude）協作開發的。本文依專案的開發紀錄整理，文字由 AI 協助撰寫，經我審閱後發布。文中不含公司、客戶或機型名稱，程式碼皆為示意。

為什麼會誤判

  • Modbus 太普及了，「TCP＋讀寫暫存器」的操作模式幾乎直接聯想到它。
  • 規格文件的位址表常同時列出兩欄，例如「PC 位址」和「MODBUS 位址」。但其中一欄可能只是作者自己的註記，並不代表通訊協議真的是 Modbus。
  • 自訂協議可以做得「外觀像」：同樣是 TCP、同樣有位址和數值，內部的封包結構卻完全不同。

五件事

1. 預設它是自訂協議

不要一開始就用標準函式庫試連線。先假設是自訂的，等證據顯示它真的是 Modbus，再切換。這個預設值的差別，在於連不上的時候你會往對的方向找原因。

2. 找規格文件，並確認哪一段是你這個機型的

文件常常混雜好幾個機型。先釐清哪些內容屬於自己手上的這台，位址欄位也要看清楚用的是哪一欄：實際要用的是「PC 位址」，不是看起來比較眼熟的那一欄。

3. 找前人留下的逆向範例

能動、但幾乎沒有註解的舊程式，價值比想像中高。用它實際送出的封包做 hex dump，再跟文件對照，比單靠啃文件更快確認真實行為。

4. 對照三個常見特徵

不是每個機型都一樣，但值得先檢查：

  • 封包是固定長度，而不是 Modbus 那種長度會變的 PDU。
  • Checksum 是自己算的，常見是加總或 XOR，而不是標準 CRC16。
  • 指令碼是自訂的，不是 Modbus 的 function code。

5. 先原封不動重送範例封包

在動手寫自己的協議層之前，先確認「照著範例送一模一樣的封包，對方會回應」。確認這一步通了，再一次只改一個欄位，觀察回應怎麼變。

import socket

def hexdump(b: bytes) -> str:
    return " ".join(f"{x:02X}" for x in b)

# 示意：把範例程式實際送出的封包原樣貼進來
FRAME_HEX = "AA 01 00 10 00 02 00"

with socket.create_connection((HOST, PORT), timeout=2) as s:
    s.sendall(bytes.fromhex(FRAME_HEX))
    print("RX", hexdump(s.recv(256)))

需要自己組封包時，常見的 checksum 寫起來通常很短，下面是兩種示意。一樣的道理：先拿範例封包驗證自己算出來的值跟它的一不一樣，再相信自己的實作。

def checksum_sum8(payload: bytes) -> int:
    return sum(payload) & 0xFF

def checksum_xor(payload: bytes) -> int:
    c = 0
    for b in payload:
        c ^= b
    return c

結語

同一個坑踩兩次，不是因為不知道，而是兩次的情境剛好都「看起來像 Modbus」。把檢查清單寫下來、放在開新專案時一定會看到的地方，比記在腦袋裡可靠得多。

開新機台的第一步不是寫連線程式，而是先問：它真的是我以為的那個協議嗎？
