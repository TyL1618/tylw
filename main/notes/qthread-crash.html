程式「什麼都沒做就自己閃退」：從當機紀錄追到 Qt 執行緒的 race condition

2026-07　・　儀器軟體／穩定性

  • PyQt
  • 多執行緒
  • QThreadPool
  • 當機分析
  • Windows 事件檢視器

AI 協作標示　這個專案是我與 AI 助手（Claude）協作開發的。本文依專案的開發紀錄整理，文字由 AI 協助撰寫，經我審閱後發布。文中不含公司、客戶或機型名稱，程式碼皆為示意。

症狀

桌面程式放著不動，掛在副螢幕上，過一陣子「什麼都沒做就自己閃退」。沒有錯誤視窗，只是消失。

我們先前把閃退歸因於「同步的網路呼叫夾在兩個對話框之間」，修完之後還是閃退。這是這次最重要的提醒：第一個看起來合理的解釋，不一定是真的。

決定性的證據：當機紀錄

Windows 事件檢視器裡有三筆 python.exe 的當機紀錄，三筆的特徵完全一致：

  • 出錯的模組：Qt6Core.dll
  • 例外代碼：0xc0000409
  • 出錯的位移：三次都是同一個

關鍵在 0xc0000409：它是 STATUS_STACK_BUFFER_OVERRUN，也就是 Windows 的 __fastfail 機制。這不是記憶體被寫壞，而是程式自己主動呼叫 abort 自殺。三次位移完全相同，代表每次都死在同一個檢查點。Qt 只有在確認自己的不變式被違反時才會這樣做，其中之一就是「一個仍在執行的執行緒物件被銷毀」。

根因

舊版的非同步工具要求每個呼叫端自己保管執行緒物件的參照，每處都寫成類似這樣：

thread, worker = run_async(fn, callback, *args)
entry = (thread, worker)
self._workers.append(entry)
thread.finished.connect(lambda: self._workers.remove(entry))   # 危險

QThread 的 finished 訊號是在「事件迴圈已經結束、但原生執行緒還沒有真正終止」的空檔發出的。最後那行 lambda 就在這個瞬間移走了最後一個 Python 參照，物件被銷毀；Qt 看到一個還在跑的執行緒被銷毀，直接 abort。

這是 race condition，時序剛好對上才會炸，所以是偶發的。而背景輪詢的計時器每隔幾秒就會生出一條新執行緒，等於一直在賭這個 race。這完全對應「什麼都沒做、放著就閃退」。

根治：不再自己管執行緒的生命週期

把整個非同步工具改成 QThreadPool ＋ QRunnable：執行緒由 Qt 自己建立、重用、回收，Python 這邊完全沒有執行緒物件的生命週期要管，race condition 從源頭消失。連帶的好處：

  • 不必每次查詢都建立一條新的作業系統執行緒（輪詢改成每 500 ms 之後，這件事變得重要）。
  • 七個檔案、十處樣板程式碼一併簡化，所有「自己保管 worker 清單」的程式碼都移除。
  • callback 包上 RuntimeError 保護：查詢還在飛的時候使用者把視窗關掉，不會再丟例外。

關閉視窗的流程也補了一步：先停掉輪詢計時器，再等既有的查詢收尾。不然關閉過程中每 500 ms 還會再丟出一輪新查詢，永遠等不完。

順便做的：把「查詢頻率」改成跟機台數量脫鉤

我希望資料刷新越快越好，所以輪詢從 2～3 秒改成 500 ms。但不能只改計時器的數字：原本每一輪是「每台機器各查一次」，每個查詢都是獨立的背景工作。改成一條連線、兩個查詢就把所有機台的資料整批查回來，連線數和機台數量完全脫鉤。實測查回一台耗時約 0.12 秒，8 秒內回呼觸發 15 次，符合預期。

帶走的幾件事

  • 遇到沒有錯誤訊息的閃退，先去看作業系統留下的當機紀錄。例外代碼與位移是否每次一致，直接告訴你是隨機的記憶體問題，還是同一個地方的主動中止。
  • 需要「每個呼叫端自己記得收尾」的設計，遲早有人漏掉。把責任收回給框架。
  • 第一個合理的解釋被推翻時，不要把它當成失敗，那是在縮小範圍。
